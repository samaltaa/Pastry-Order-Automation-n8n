Stage 1 Overview

Pastry Ops Automation

A lightweight AI automation system for handling pastry orders, grounded in real menu data, orchestrated with n8n, validated by a Fastify backend, and stored durably in PostgreSQL.

Webhook intake Structured extraction Grounding Idempotency Docker orchestration

1. System overview

flowchart LR
    A[Customer message] --> B[Telegram webhook]
    B --> C[n8n workflow]
    C --> D[Check duplicate update]
    D --> E[Load conversation state]
    E --> F[LLM structured extraction]
    F --> G[Validate against menu + rules]
    G --> H{Valid?}
    H -->|No| I[Ask clarifying question]
    H -->|Yes| J[Fastify API /orders]
    J --> K[Postgres: orders + order_items]
    K --> L[Confirmation to customer]

This is the core architecture pattern: the user message enters through a message channel, n8n handles the flow, and the backend service enforces the rules. The LLM is used for understanding, but not for deciding prices or business policy.

2. Why this design exists

n8n Orchestrates triggers, branches, message handling, and workflow logic. It is the automation control plane.
Fastify Owns validation, business rules, persistence logic, and stable API contracts.
PostgreSQL Stores the menu, customer records, orders, item lines, dedupe keys, and conversation state.
LLM Interprets language and returns a structured order payload, but does not decide pricing or policy.
The key interview principle: orchestration is not business logic. Business logic belongs in a service with tests and validation.

3. Grounding: menu and pricing come from the database

flowchart TD
    A[Customer request] --> B[LLM extraction]
    B --> C[Menu rows from Postgres]
    C --> D[Map request to item_id]
    D --> E[Compute total in code]
    E --> F[Write order to database]

Grounding means the model sees a real catalog of menu items and must map the request to known product IDs. The app never asks the LLM to invent a product or choose a price. Pricing is computed from the DB and tested in code.

  • Products are stored in menu_items
  • Orders reference menu item IDs, not free-form names
  • The total is computed in the backend, not by the model
  • Unknown products are rejected or clarified

4. Server request lifecycle

flowchart LR
    A[Incoming HTTP request] --> B[Fastify route handler]
    B --> C[Validate request schema with Zod]
    C --> D[Query Postgres for menu rows]
    D --> E[Reject invalid or unknown items]
    E --> F[Compute total]
    F --> G[Insert customer, order, items]
    G --> H[Return JSON response]

The server acts as the guardrail layer. It handles validation, pricing, and writes. This keeps the workflow correct even when the model behaves imperfectly.

5. Idempotency and duplicate protection

flowchart TD
    A[Webhook arrives] --> B[Check update_id or idempotency_key]
    B --> C{Seen before?}
    C -->|Yes| D[Ignore duplicate]
    C -->|No| E[Process order]
    E --> F[Persist processed id]
    F --> G[Return success]

Webhooks can be retried. Duplicate deliveries are a normal production issue. This project prevents double-booking and duplicate orders by recording the source event ID, then ignoring repeats.

6. Docker and local environment

flowchart LR
    A[Developer machine] --> B[docker compose]
    B --> C[postgres container]
    B --> D[n8n container]
    B --> E[ops-api container]
    B --> F[cloudflared container]

    D --> G[Webhook trigger]
    E --> H[API endpoints]
    C --> I[Database tables]
    G --> H
    H --> C

Docker Compose gives a single runtime model: Postgres provides state, n8n provides orchestration, and the Fastify service provides business behavior. The cloudflared service exposes the local webhook endpoint externally when needed.

7. End-to-end order flow

sequenceDiagram
    participant Customer
    participant Telegram
    participant n8n
    participant API
    participant Postgres

    Customer->>Telegram: Sends order text
    Telegram->>n8n: Webhook event
    n8n->>n8n: Check duplicate update
    n8n->>API: POST /llm/extract-order
    API->>Postgres: Load menu catalog
    API-->>n8n: Extracted order payload
    n8n->>n8n: Validate items and timing
    n8n->>API: POST /orders
    API->>Postgres: Validate ids and compute total
    API->>Postgres: Insert customer and order rows
    API-->>n8n: Success / duplicate / error
    n8n->>Telegram: Send confirmation or clarification

This end-to-end flow is exactly what an interviewer wants to hear: request enters the system, gets interpreted, validated, persisted, then confirmed back to the user.

8. Core patterns to study

Pattern What it means Why it matters
Webhook-first design External systems trigger event-driven automation Customer events are asynchronous and sometimes retried
Grounding LLM works with real database data instead of free assumptions Reduces hallucination and priced mistakes
Structured extraction Model returns a machine-readable payload with predictable keys Validation and downstream automation become reliable
Idempotency Duplicate events are rejected or safely ignored Prevents double-charging and double-orders
Separation of duties n8n orchestrates, API validates, DB stores truth Clearer system design and easier troubleshooting

9. The most important interview statement

This system uses n8n to orchestrate messages, a Fastify API to enforce business rules, and PostgreSQL as the source of truth. The model only interprets language. The backend validates item IDs, computes totals, and prevents duplicate writes.
