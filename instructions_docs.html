01 · The system

The system at a glance

Four containers run on your laptop under Docker Compose. One of them opens a public door so Telegram can reach in.

A customer types "2 tres leches for tomorrow at 3pm" into Telegram. Telegram's servers wrap that text in a JSON update and POST it to the webhook URL you registered. That URL belongs to a Cloudflare quick tunnel, which forwards the request to the n8n container on your laptop.

n8n runs the Order intake workflow. It checks that the request really came from Telegram, claims the update so a retry can't be processed twice, and sends commands like /start to the menu branch. Everything else goes to ops-api, which loads the live menu, asks Claude to turn the sentence into structured items, and checks the result against the bakery's rules in code. If the draft passes, ops-api prices it from Postgres and saves it in one transaction. n8n then confirms the order or asks a clarifying question through the Telegram Bot API.

The LLM turns words into item IDs. Code turns item IDs into money.

The life of one message

  1. Customer sends a message to @Pastryandmiscbot.
  2. Telegram POSTs the update, with your secret token in a header.
  3. cloudflared forwards it to n8n:5678/webhook/order-intake.
  4. n8n verifies the secret, then claims update_id (POST /updates/claim). A retry stops here.
  5. /start and /menu get the menu. Anything else goes to /llm/extract-order.
  6. Claude Haiku 5.5 extracts the order. Code checks it, and Sonnet 5.5 steps in only if Haiku fails.
  7. /orders prices the order from the database and saves it once, inside one transaction.
  8. n8n confirms, asks a question, or apologizes if something broke.

The four services

postgrespastry-postgreslocalhost:5432postgres:5432Database pastry_ops. Holds the menu, customers and orders, plus n8n's own workflows, credentials and execution history.

Two addresses for one API

Inside Docker, containers reach each other by service name, so n8n calls http://ops-api:3001. From your browser, the same API is at http://localhost:3002, because Grafana already uses port 3001 on this laptop. API_PORT in .env only changes the laptop-side port.

Why the layers sit where they do

n8n kept the jobs it's good at: triggers, routing, retries, replies and schedules. Anything that needs a test, a transaction or a secret went into ops-api. That's why dedupe is an API call and not an n8n Postgres node: the rule lives in one place, with one credential, and can be tested.

Mapped to the job description

  • n8n in production: two active workflows with error branches.
  • Backend + webhooks: Fastify, Zod, an API key and idempotent POSTs.
  • Model selection by cost and quality: the eval table and ADR 001.
  • Fewer hallucinations: grounding, a schema, code rules and injection tests.
  • PostgreSQL: transactions, migrations and the cost log.
  • Documentation: this manual, the ADR and the eval report.

03 · The workflow

Inside the order-intake workflow

Fourteen nodes: gatekeeping first, then a menu branch and an order branch. This is the "Order intake" workflow as it appears in the n8n editor, split into two parts to fit the page.

Node by node

Reading n8n expressions

Anything inside {{ }} is JavaScript. $json is the data coming into the current node. $('Telegram webhook').first() reaches back to an earlier node by its display name. That's why the chat ID and update_id are always read from the trigger node, whatever ran in between.

Renaming a node breaks things

Expressions find other nodes by name. If you rename "Telegram webhook", every $('Telegram webhook') in later nodes stops working. Recent n8n versions offer to update those references when you rename. Check every node anyway.

04 · The menu

The menu is a table

No config file holds the menu, and nothing is hardcoded in the workflow. The menu lives in Postgres, and every message reads it fresh.

Your dishes live in the menu_items table of the pastry_ops database. Two parts of the code read it. GET /menu returns the active dishes for the /start reply. POST /llm/extract-order loads them for Claude's prompt (names and IDs only, never prices). POST /orders looks up prices by ID when it computes a total. Because both read the table on every request, a change takes effect on the next message. You don't need to restart, rebuild or re-import anything.

The six starter dishes came from the end of db/001_init.sql. That file only runs the first time Postgres starts with an empty volume. Editing it now won't change your running menu. It only changes what a fresh install starts with.

The columns

ColumnMeaning
idAssigned automatically. The LLM must answer with these IDs, and orders reference them.
item_nameWhat customers see and what the LLM matches against.
categoryA free-text label: cake, savory, bread…
priceIn RD$, with two decimals.
is_activeSet to false to hide a dish without deleting it.

View the menu

From the API, which is what the bot sees. The API requires the key, so a plain browser tab gets a 401:

set -a; source .env; set +a curl -H "x-api-key: $OPS_API_KEY" localhost:3002/menu

In Telegram: send /menu to the bot.

In n8n: open any run under Executions and click the Load menu node to see its output.

In the database, which also shows hidden dishes:

# open a SQL prompt (\q to quit) docker compose exec postgres psql -U pastry -d pastry_ops SELECT id, item_name, category, price, is_active FROM menu_items ORDER BY id;

Change the menu

Run these from the same SQL prompt.

-- add a dish INSERT INTO menu_items (item_name, category, price) VALUES ('Flan de caramelo', 'dessert', 250.00); -- change a price UPDATE menu_items SET price = 700 WHERE id = 1; -- take a dish off the menu UPDATE menu_items SET is_active = false WHERE id = 5;

Hide dishes, don't delete them

Each line of an order points at a menu_items.id. Once a dish has been ordered, Postgres refuses to delete it, and that's intentional. Set is_active = false instead.

Old orders keep old prices

When an order is created, each line copies the price at that moment into order_items.unit_price. A price change only affects new orders.

Want a fresh install to start with your real menu? Make the same change to the INSERT at the bottom of db/001_init.sql and commit it. The course plan moves this into db/seed.sql later.

05 · Editing n8n

Changing a workflow

Every workflow exists twice: the live copy n8n runs, and the JSON file git remembers. Edit the live copy, then export it to the file.

n8n stores workflows in its own tables inside Postgres. Telegram only ever reaches that live copy. The JSON in n8n/workflows/ is a backup that you can keep in version control and review like code. The two don't sync on their own, so make it a habit: edit in the editor, then download into the repo and commit.

Method A — the editor (use this one)

  1. Open n8n. Go to http://localhost:5678 (or the tunnel URL) and log in with your owner account.
  2. Open the workflow. Click Overview → Workflows → Order intake.
  3. Make the change. Double-click a node to edit it, drag from an output dot to add a connection, and hover over a connection then click the bin icon to delete it. Press Tab or click + to add a node.
  4. Save with Ctrl+S. The workflow is already active, so saving puts the change live immediately.
  5. Test it for real. Message the bot, then open Executions (top tab). Every run is listed there. Click one to see which path it took and the data at each node. A red node is where it failed.
  6. Export. Click ⋯ (top right) → Download, and save it over n8n/workflows/order-intake.json.
  7. Commit. Run git diff to review the change, then commit. The file contains the credential's name and ID but never the token itself.

Testing without your phone

Telegram only knows the production URL (/webhook/…). The editor's Test workflow button listens on a separate test URL (/webhook-test/…) that Telegram never calls. To test inside the editor, open a past execution, copy the Telegram webhook output, go back to the editor, and use Pin data on the trigger node to paste it there. Test workflow then reruns the flow on that real message as many times as you like. Unpin the data before you rely on live traffic again.

Method B — load the file into n8n

Use this to restore from git or to set up a new machine.

  • Editor: Workflows → Create → ⋯ → Import from File. This makes a new workflow with a new ID. Deactivate the old one, because two active workflows can't share the webhook path.
  • Command line (keeps the ID pastryOrderIntake): copy the file into the container, wrap it in a JSON array (the CLI requires an array), run n8n import:workflow, then n8n update:workflow --id=pastryOrderIntake --active=true, then docker compose restart n8n. This is how the MVP was first loaded.

Changes that need extra steps

  • The webhook path on the trigger node: register the new URL with Telegram again (§08).
  • Deactivating the workflow: Telegram's requests get a 404 until you activate it again.
  • Calling the API: use http://ops-api:3001. localhost inside n8n means the n8n container itself.
  • New credentials go in Overview → Credentials. They're encrypted with N8N_ENCRYPTION_KEY.

Environment variables in nodes

n8n can read any variable from .env as $env.NAME. That's how the Verify node compares the secret. Edit .env, then run docker compose up -d n8n. Store secrets you use often as credentials instead.

06 · The backend

Changing the API

Every rule that touches money lives in one TypeScript file. Edit it, rebuild one container, and test with the browser or curl.

The three files of ops-api

src/server.tsSetup, auth hook, error handlerRefuses to start without OPS_API_KEY. Every route except /health needs x-api-key. Zod errors become 400s with a list of issues.
RoutesGET /health · GET /menu · POST /updates/claim · POST /llm/extract-order · POST /orders (idempotent, one transaction) · GET /orders/:id · POST /orders/:id/status (a fixed set of statuses) · GET /reports/prep-list · GET /reports/llm-usage

RoutingTries ANTHROPIC_MODEL_FAST, then ANTHROPIC_MODEL_STRONG on an API error, a refusal, an unknown ID, a malformed time, or low confidence on a draft that would otherwise be accepted.

The edit loop

# 1. type-check cd ops-api && npx tsc --noEmit && cd .. # 2. rebuild and restart only the API docker compose up -d --build ops-api # 3. watch it boot / see errors docker compose logs -f ops-api # 4. poke it curl localhost:3002/health # 5. after any prompt, rule or model change cd ops-api && node --env-file=../.env \ --import tsx ../evals/run.ts

n8n doesn't need restarting. Its next HTTP call reaches the new API.

The extraction contract

The workflow depends on /llm/extract-order returning this shape. If you change it, update the nodes that read it.

FieldUsed by
valid (boolean)Validate extracted order
items[] of {item_id, quantity}Create order via API
delivery_address, delivery_at (local YYYY-MM-DDTHH:mm)Create order via API
customer_name, customer_phone, notesOptional. Defaults are applied in n8n.
clarificationAsk clarifying question
violations, model, escalatedDebugging in Executions

The prices the customer pays never pass through the model. Even a perfectly successful prompt injection can only pick menu IDs, and code still checks those.

Running outside Docker

npm run dev in ops-api/ gives hot reload, but it reads ops-api/.env. Its DATABASE_URL must point at localhost:5432, because the host name postgres only exists inside Docker. Stop the container first, or use a different PORT.

Where the file is headed

07 · Tutorial

The /start menu branch

This branch is now live. When someone taps Start, the bot replies with the menu instead of reading it as an order. This page explains how it was built, so you can rebuild it from a blank canvas as practice.

The bug this fixed

When someone taps Start, Telegram sends an ordinary message with the text /start. In the MVP that went straight into the order flow, and the demo extractor turned it into an order, so every new customer created a fake order. In the live version the Switch sits after First delivery? and its rule also matches /menu and menu. The steps below use the simpler two-node version shown in the diagram.

Rebuild drill (on a copy of the workflow)

  1. Back up first. Open Order intake, then ⋯ → Download. If anything goes wrong, Method B in §05 puts this copy back.
  2. Cut the old wire. Hover over the connection from Verify Telegram update (true) to Load menu and click the bin icon.
  3. Add the router. Drag from Verify's true output, search for Switch, and rename the node Route command. Set Mode to Rules. Add one rule:
    • Value: an expression that reads the message text from the trigger node. Copy how Send confirmation reaches the trigger, but end with .message.text instead of .message.chat.id.
    • Operation: String → starts with /start
    • Turn on Rename Output and call it /start.
    Under Options, set Fallback Output to Extra Output and rename it fallback.
  4. Re-attach the order flow. Drag from the fallback output onto Load menu. Ordinary messages now take exactly the same path as before.
  5. Fetch the menu. From the /start output, add an HTTP Request node named Get menu for /start, with Method GET and URL http://ops-api:3001/menu. Duplicating Load menu (Ctrl+D) and renaming the copy also works.
  6. Combine the dishes. Add an Aggregate node named Combine menu items, set Aggregate to All Item Data (Into a Single List), and set the output field to menu.
  7. Send it. Add a Telegram → Send Message node named Send menu. Pick the Pastry Telegram bot credential. Copy Chat ID from Send confirmation. For Text, write an expression that turns $json.menu into one line per dish (name and price in RD$), joined with line breaks, under a short greeting. Under Additional Fields, turn Append n8n Attribution off.
  8. Save and test. Press Ctrl+S, then send /start to the bot. In Executions, the run should take the top path and never touch Create order via API.
  9. Advertise the command. This one is still for you to do: in @BotFather, send /setcommands, pick your bot, and send menu - See today's menu. Telegram then shows it in the bot's Menu button.
  10. Export and commit. Download over n8n/workflows/order-intake.json and commit with a message like "Route /start to menu reply".

Why each piece is there

  • Why a Switch, not an IF? More commands are coming (/menu, /status, /help). A Switch takes one more rule per command, while IFs would have to be chained.
  • Why not reuse "Load menu"? A node sends its output down every connection it has. Wiring it to both branches would run the order flow on /start too.
  • Why Aggregate? The menu request returns six items. A Telegram node runs once per item, so without Aggregate the customer would get six separate messages.
  • Why route before the LLM? Commands are free to recognise and LLM calls aren't. Handle anything you can recognise with plain rules before paying for a model.

Done when

  • /start gets exactly one message listing every active dish with its price.
  • No new row appears in orders after /start.
  • A normal order message still gets a confirmation.
  • After a price change in psql, the next /start shows the new price.
  • The exported JSON is committed.

Stretch goals

  • Add a /status rule that looks up the customer's latest order with GET /orders/:id.
  • Group dishes by category in the message, and use Parse Mode HTML for bold headings.
  • Add /help as a third output that replies with an example order.

After every reboot: the tunnel dance

The quick tunnel gets a new random URL each time it starts, and Telegram is still pointing at the old one. Do these four steps whenever the URL changes:

  1. Start and read the URL. Run docker compose up -d, wait about ten seconds, then grep the cloudflared logs as shown above.
  2. Update .env. Set WEBHOOK_URL=https://…trycloudflare.com/, keeping the trailing slash.
  3. Restart n8n: docker compose up -d n8n.
  4. Re-register with Telegram:
    set -a; source .env; set +a curl "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook" \ -d url="${WEBHOOK_URL}webhook/order-intake" \ -d secret_token="$TELEGRAM_WEBHOOK_SECRET"

A named Cloudflare tunnel on your own domain makes the URL permanent and removes these steps. The course does that in Stage 3, with Caddy on a VPS.

The danger zone

  • docker compose down -v deletes both volumes: every order, the menu, and every n8n workflow and credential.
  • Changing N8N_ENCRYPTION_KEY makes every stored credential unreadable.
  • Changing POSTGRES_PASSWORD after the first start locks n8n and the API out of the database. The old password is still the real one.
  • Pasting real keys into .env.example commits them to git.

12 · Conversation memory

How the bot remembers

Customers answer one question at a time, change their minds, and come back next week. The bot keeps a small, structured memory for each chat in Postgres, so nobody has to repeat themselves.

When memory changes

Every messageThe draft is replaced with Claude's updated version. The message and the bot's reply are added to the history, which keeps only the last 6 entries.
Order createdPOST /orders deletes the chat's conversation and saves customers.last_address, in the same transaction as the order.
/cancelAlso "cancel" or "cancelar". n8n calls POST /conversations/reset, and the draft and history are deleted.
2 hours of silenceThe row stays, but the next message ignores it and starts fresh. Old half-orders don't come back.

What is stored

One row per chat in conversations, keyed by chat_id:

state = { "draft": { items, delivery_address, delivery_at, notes, … }, "history": [ { role: "customer", text }, { role: "bot", text }, … (last 6) ] } last_message · updated_at

To see it live:

docker compose exec postgres psql -U pastry \ -d pastry_ops -c "select chat_id, state, updated_at from conversations;"

Why a draft, not the whole chat log

Claude gets a compact draft plus 6 recent messages, so the cost stays flat however long the chat runs (about $0.0003 per message). The draft is structured data that the rules can check. Only order facts go back to the model, never the previous turn's flags, which stops stale "needs clarification" flags from sticking around. The eval caught exactly that bug.

Where it lives

  • ops-api/src/conversation.ts: history limit, 2-hour expiry, advance()
  • src/llm/extract.ts: draft and conversation in the prompt, treated as data
  • src/rules.ts: the saved-address offer
  • src/server.ts: lock, load, save, reset, and clear on order
  • db/003_conversations.sql: unique chat_id, customers.last_address
  • evals/cases.jsonl: 10 multi-turn cases mt-01…mt-10, 10/10 passing

Things to know

  • The lock holds a database connection during the Claude call (about 2 s). That's fine at bakery scale. At high volume, the next step is a queue per chat.
  • Tune HISTORY_LIMIT and STATE_TTL_HOURS in conversation.ts, then run the eval.
